# ADR-001: Реальные групповые чаты (не демо)

**Статус:** Accepted (2026-07-07) — вариант A, поэтапная реализация с чекпоинтами.
Forward secrecy для групп сознательно вынесен в отдельный будущий ADR (см. §
«Рассмотренные варианты» → Вариант B) — не блокирует текущую работу.
**Дата:** 2026-07-07
**Решает:** Sebastian (владелец продукта)

## Контекст

Сейчас в проекте есть только UI-мокап групповых чатов (тумблер в создании чата,
лимит участников, экран профиля группы — всё на демо-данных). Пользователь хочет
включить это по-настоящему и считает, что «синхронизация уже есть».

Я проверил это прямо в коде (не по памяти), и это **частично верно**:

### Уже N-party-готово (проверено)

- **`NostrTransport`** — все события помечаны одним тегом `#t channelId`
  (`appendLine`: `tags = listOf(listOf("t", channelId))`). Чтение с реле — это
  **union по тегу**, не привязанное к конкретной паре pubkey. Т.е. сколько угодно
  участников могут публиковать/читать события одного канала уже сегодня.
- **`profiles.txt`** — NIP-78 replaceable-события, **по одному слоту на pubkey**,
  чтение уже собирает **все** слоты (`AllChannelData.profileSlots`) — это специально
  сделано для нескольких участников (см. комментарий в `NostrTransport.kt` —
  «Все слоты profiles.txt (по одному на участника) — источник union-чтения»).
- **`ProfileSync`** — внутренняя модель уже `Map<userId, Profile>` на chatId
  (не «self + partner»), включая **персональный `lastReadIndex` на каждого**
  участника. Это уже N-party по структуре данных.
- **`InviteCodec`** (v3) — инвайт с PIN, ничего в формате не привязано к «ровно
  одному» новому участнику; лимит участников просто нигде не проверяется.
- **`AppDatabase`** — 12 последовательных Room-миграций, `fallbackToDestructiveMigration()`
  как страховка. Добавление новой сущности — обкатанный, недорогой паттерн здесь.

### НЕ готово (реальные блокеры)

1. **`Chat` (Room-сущность)** — жёстко на одного собеседника: `partnerName`,
   `partnerTag`, `partnerAvatarBase64`, `partnerJoined`, `partnerLastReadIndex`,
   `myEphemeralPubKeyB64`/`partnerEphemeralPubKeyB64`. Это и есть настоящий блокер
   данных, не транспорт.
2. **Криптография forward secrecy (V3 / V4-S)** — `X25519 ECDH`, общий секрет
   вычисляется строго из **двух** ключевых пар. Математически не расширяется на
   N участников без отдельного протокола (sender-keys / MLS / N-кратный pairwise
   fan-out). Это подтверждает риск, о котором писал CLAUDE.md.
3. **V4 / V5 (Argon2id + AES-GCM, общий пароль чата)** — это, наоборот, **уже
   N-party по конструкции**: любой, кто знает `chatPassword`, шифрует/расшифровывает.
   Именно так работает сам инвайт до апгрейда на forward secrecy в 1:1-чатах.
4. **UI-слой** (`ChatActivity` — 181 упоминание `partner*`, `MessageAdapter`,
   `PartnerProfileActivity`) — везде «один собеседник», а не список участников.
5. **Управление группой (admin/ban)** — не существует вообще, нужно строить с нуля.

## Решение (рекомендация)

Строить группы **аддитивно**, не трогая 1:1-путь — чтобы гарантии CLAUDE.md §1
(«синхронизация неприкосновенна», обратная совместимость) выполнялись буквально:
ни один байт в `V1–V4-S` decrypt-путях не меняется, старые чаты не задеты.

1. **Room:** миграция 12→13 — новая сущность `ChatParticipant` (chatId, userId,
   displayName, avatarB64, isAdmin, banned, joinedAtMs) + новые колонки в `Chat`
   (`isGroup: Boolean = false`, `participantLimit: Int? = null`, `adminPubkeyHex: String? = null`)
   — все с дефолтами, старые строки не трогаются.
2. **Криптографии для групп — отдельного кода НЕ нужно.** Проверил в `ChatActivity.kt`
   (строки ~495-520, ~2725-2759): ECDH forward-secrecy апгрейд (`generateEphemeralKeyPair`
   → `tryEstablishSessionKey` → `CryptoHelper.setSessionKey`) — это отдельный шаг,
   который запускается явно поверх уже созданного `channelId`/`chatPassword`. Если для
   группового чата (`chat.isGroup == true`) просто НЕ запускать этот блок, `CryptoHelper.encrypt()`
   сам продолжит использовать V5 (Argon2id + пароль) — тот же путь, что уже работает у
   1:1-чатов ДО рукопожатия. Значит: используем существующий `NostrTransport(channelId,
   password, myUserId)` и существующий `generateChannelId()`/`generatedPassword` без единой
   новой крипто-функции — просто участники группы держат один и тот же `chatPassword`
   (полученный из инвайта), и никто из них не проходит ECDH-апгрейд. Это даёт мгновенное
   O(1)-шифрование на сообщение (как требует §13), а не O(N) фан-аут на каждого участника.
3. **Управление/бан:** новый подписанный файл `members.txt` на канал, пишет
   только приватный ключ администратора (тот же per-chat ключ, которым уже
   подписываются kind:1-события) — `{version, participants:[{userId, banned}], ts}`.
   Проверка подписи — тот же паттерн, что уже есть в `RelayListStore`
   (доверенный якорь + анти-откат по версии), только per-chat, а не глобально.
   **Бан = «мягкий» (реализовано, см. §Последствия/Action items):** `members.txt`
   помечает `banned=true`. Это (а) блокирует повторный вход по инвайту
   (`JoinChatActivity`), (б) триггерит локальное автоудаление чата на устройстве
   забаненного, как только его клиент увидит свой бан (`ChatActivity.checkSelfBanned`),
   (в) скрывает НОВЫЕ сообщения забаненного из ленты у остальных участников на
   уровне отображения (`ChatActivity.processChannelData` — фильтр по `senderUserId`
   в списке банов, не декрипту). Ротация пароля **сознательно не делается** в MVP:
   доставить НОВЫЙ пароль оставшимся участникам так, чтобы забаненный (знающий
   текущий пароль) не смог его тоже перехватить, невозможно без попарного
   шифрования — то есть без Варианта B (см. ниже). Поэтому крипто-доступ
   технически не отзывается: если забаненный продолжит слушать реле мимо
   собственного клиента (модифицированный клиент), он всё ещё может
   расшифровать историю/новый контент, зная общий пароль. Это явный,
   раскрываемый пользователю компромисс MVP, а не забытый недочёт.

   **Разбан (реализовано):** админ видит забаненных в списке участников
   (`PartnerProfileActivity`, дублирующий пункт §Действия ниже) и может снять
   `banned=false` — публикует новую версию `members.txt`. Пользователю явно
   подтверждено и принято: разбан НЕ меняет пароль и НЕ даёт избирательного
   доступа к старой истории (см. выше — тот же общий пароль, что и всегда) —
   разбаненный при повторном входе видит всё то же, что видел бы новый участник.
   Разбан также не возвращает человека в чат автоматически: его локальный чат и
   секреты уже удалены на его устройстве в момент бана, поэтому администратору
   нужно заново поделиться приглашением (тот же канал/пароль, `ChatsListActivity`).
4. **Переиспользуется без изменений:** `ProfileSync`, `NostrTransport` (тег/юнион-чтение),
   `PatchQueue`, `SyncEngine` (единый polling), `InviteCodec` (добавить только
   клиентскую проверку лимита участников).
5. **UI:** `ChatActivity`/`MessageAdapter`/`PartnerProfileActivity` ветвятся по
   `chat.isGroup`, реальные данные вместо уже собранного демо-каркаса.

## Рассмотренные варианты

### Вариант A — MVP: общий пароль (V5), без forward secrecy, реальный membership/бан (рекомендую)

| Критерий | Оценка |
|---|---|
| Сложность | Средняя |
| Риск для 1:1-кода | Практически нулевой (полностью изолировано) |
| Скорость отправки | O(1) на сообщение — соответствует §13 |
| Время до первой рабочей версии | Недели, не месяцы |

**Плюсы:** реальное E2E-шифрование группы уже сейчас, проверенные примитивы,
не трогает §1-защищённый код. FS можно добавить позже отдельным ADR — формат
уже автоопределяется по префиксу в `decrypt()`.
**Минусы:** нет forward secrecy — утечка пароля группы расшифровывает всю
историю задним числом (тот же уровень доверия, что у 1:1 чата до апгрейда).

### Вариант B — Полноценный N-party forward secrecy сразу (sender-keys / MLS-подобная схема)

**Сложность:** высокая/очень высокая — новый протокол, новый wire-формат,
требует отдельного крипто-ревью. Недели-месяцы до первой рабочей версии.
**Плюсы:** настоящая FS для групп с первого дня.
**Минусы:** блокирует любую доставку функции надолго, выше риск тонких уязвимостей
в самодельном multi-party протоколе.

### Вариант C — «Фейковая» группа: N независимых 1:1-веток под одним UI

**Сложность:** средне-высокая. Трафик растёт O(N) на сообщение через Tor —
на 10–15 участниках это прямо нарушает §13 («мгновенно, без ощущения загрузки»).
**Минусы:** не рекомендую — конфликтует с фундаментальным принципом продукта.

**Рекомендация: Вариант A.**

## Анализ компромиссов

Вариант A жертвует forward secrecy ради N-party и скорости. Это осознанный,
явно раскрываемый компромисс — совпадает с тем, как уже ведут себя 1:1-чаты до
ECDH-рукопожатия. Бан реализован как «мягкий»: `members.txt` (banned=true) +
блокировка повторного входа + автоудаление чата у забаненного + скрытие его
новых сообщений в ленте у остальных на уровне отображения. Криптографического
отзыва доступа (ротация пароля) в MVP нет — см. §Контроль/Управление выше
и пункт "Технический долг" ниже.

## Последствия

- **Проще:** список участников, админ-права, реальный бан — обычные Room-запросы
  после появления `ChatParticipant`.
- **Сложнее:** любая будущая работа над FS для групп потребует второй миграции/протокола.
- **Пересмотреть позже:** лимит участников — best-effort на клиенте (без
  криптографического принуждения против недобросовестного реле/гонки джойнов) —
  приемлемо, т.к. это тот же уровень доверия, что и у текущего инвайт-кода.

### Технический долг (осознанно принят, не забыт)

- **Гонка джойна вблизи лимита участников (частично смягчена).** Приём в группу
  неатомарен: `JoinChatActivity` проверяет ёмкость по (возможно устаревшему)
  `members.txt`/приближённо по `profiles.txt`, а реальное добавление в `members.txt`
  делает клиент админа фоном (`maybeAdminEnrollNewMembers`). Если несколько человек
  джойнятся одновременно у самого лимита — оба локально «входят» в чат, но слот
  реально один. Смягчено (не устранено полностью — для полного устранения нужен
  центральный арбитр, что противоречит P2P-архитектуре):
  - `maybeAdminEnrollNewMembers` теперь выбирает кандидатов в детерминированном
    FIFO-порядке по первому наблюдению админским клиентом (`groupCandidateFirstSeenMs`,
    только в памяти, не по сети), а не в нестабильном порядке итерации `Map`.
  - Участник, который не подтверждён спустя `GROUP_PENDING_BANNER_TICKS` тиков
    (`ChatActivity.checkPendingGroupEnrollment`), видит честный баннер «Ожидаем
    подтверждения» вместо тихого зависания в неопределённом состоянии.
  - Осознанно НЕТ автоудаления по таймауту: офлайн-админ выглядит для клиента
    так же, как «чат заполнен», и агрессивное авто-исключение рисковало бы выкинуть
    легитимного участника только из-за того, что админ временно не в сети. Если
    участник решит, что не попал — есть обычное действие «Удалить чат».
- **Бан не отзывает крипто-доступ.** Общий пароль группы (V5) знают все участники,
  включая забаненного. «Мягкий бан» защищает UX (не даёт переприсоединиться, скрывает
  новые сообщения забаненного у остальных, удаляет чат у него самого), но НЕ мешает
  модифицированному/недобросовестному клиенту забаненного и дальше слушать реле и
  расшифровывать контент, пока пароль не сменён вручную (пересоздание чата). Настоящая
  крипто-экслюзия требует попарного re-keying протокола — это Вариант B (см. выше),
  сознательно отложен.
- **Нет forward secrecy для групп.** V5 (общий пароль), не V4-S. Тоже Вариант B.
- **Текст сообщений в группах шифруется V4, а не V5 (найдено и исправлено по репорту
  пользователя).** Изначально `ChatActivity` шифровал строку-анонс сообщения (текст,
  подпись к фото/голосу/стикеру, правку) обычным `CryptoHelper.encrypt()`, который для
  групп (нет сессионного ключа, см. выше) ВСЕГДА падал на V5 — Argon2id (64 МБ,
  3 итерации) со случайной солью на каждый вызов, несжимаемо → полный пересчёт на
  КАЖДОЕ сообщение → «часики» висели секундами на любой отправке в группе, хотя 1:1
  после рукопожатия — мгновенно. Исправлено: `CryptoHelper.encryptGroupMessage()`
  (новая обёртка над `encryptV4`) + `ChatActivity.encryptChatLine()` — для групп текст
  сообщений теперь идёт через V4 (детерминированная соль от chatId, кэшируемый ключ),
  тот же приём, что уже использовался для `profiles.txt`/`members.txt`
  (`encryptMetadata`). 1:1 не затронуты (там как раньше `encrypt()`). Компромисс:
  соль сообщения стала детерминированной вместо случайной на каждое сообщение (чуть
  слабее защита от precompute-атак) — принят осознанно, т.к. группа и так без forward
  secrecy и с общим паролем у всех участников, так что реальная модель угроз не
  меняется. Media-контент (фото/голос/стикеры) НЕ тронут — по-прежнему через
  `encrypt()`, это отдельное, более крупное архитектурное решение (форвард-секрети
  медиа в 1:1, см. §13 CLAUDE.md), не входило в эту правку.
- **Список чатов не синхронизировал `members.txt` вообще (найдено и исправлено по
  репорту пользователя).** После фикса «список не подхватывает переименование/аву
  группы» (см. пункт действий №8 ниже) `ChatsListActivity` стал БЕЗОПАСЕН для групп
  (перестал их портить через 1:1-only `findPartner`), но не получил взамен НИКАКОГО
  активного пути синхронизации `members.txt` — единственные вызовы `MembersSync.
  applyIncoming` остались в `ChatActivity` (только при открытом чате) и разовый
  best-effort в `JoinChatActivity` в момент джойна (гоняется с публикацией админа,
  задокументированная гонка). Если тот best-effort не успевал и пользователь ни разу
  не открывал сам чат — имя/аватар оставались на seed-значении из инвайта, а таблица
  `ChatParticipant` — пустой → счётчик участников 0 везде (шапка чата, профиль),
  собеседник при этом мог полноценно переписываться (сообщения не зависят от
  `members.txt`). Исправлено: `ChatsListActivity.checkUnreadAllChats()` теперь тоже
  вызывает `MembersSync.applyIncoming` на каждом фоновом опросе (первый — сразу при
  открытии списка, дальше каждые 8с) — данные уже приходят бесплатно в существующем
  `api.loadAll()`, лишнего сетевого запроса нет.

## Пункты действий (по фазам) — статус на конец реализации

2. [x] Крипто: ECDH-рукопожатие просто не запускается для групп — `CryptoHelper.encrypt()`
   остаётся на V5 автоматически (без нового криптодомена — исходный план по отдельному
   криптодомену оказался лишним, см. правку этого ADR в процессе реализации).
3. [x] Подписанный `members.txt` (admin-only write) + проверка подписи на чтении
   (`NostrTransport.latestVerifiedMembersFile`).
4. [x] `CreateChatActivity`: реальное создание группы, детерминированный admin-ключ
   (`privkey = f(chatPassword, adminUserId)`, без отдельного хранения), первичный
   `members.txt` (v1, только админ).
5. [x] `JoinChatActivity`: проверка лимита участников + бана по `members.txt`
   (с best-effort фоллбэком на `profiles.txt`, если `members.txt` ещё не долетел);
   самодобавление — через пассивный `profiles.txt` + подхват админом
   (`maybeAdminEnrollNewMembers`), не прямой join-request.
6. [x] `ChatActivity`/`MessageAdapter`: реальный счётчик участников в шапке
   (`applyGroupHeader`/`applyGroupPresence`), read-receipt = прочитано ВСЕМИ
   (min по `lastReadIndex` среди остальных участников).
7. [x] `PartnerProfileActivity` (группа): реальные данные вместо демо (список
   участников из `ChatParticipantDao` + живые профили), реальный бан и
   переименование/смена аватара группы админом — через `MembersSync.publish`

8. [x] Пропагация бана: локальное автоудаление чата у забаненного
   (`ChatActivity.checkSelfBanned`, идемпотентно) + скрытие новых сообщений
   забаненного из ленты у остальных участников на уровне отображения
   (`ChatActivity.processChannelData`, фильтр по `senderUserId`).
9. [x] Полный аудит по CLAUDE.md §14, подъём версии, регрессия на существующих

   строго за `chat.isGroup`/`EXTRA_IS_GROUP`, для 1:1 поведение не изменилось

10. [x] Срок действия group-инвайта — степпер (−/+) в `dialog_invite_pin.xml`,
    видим только при `chat.isGroup` (1:1 не тронут, остаётся дефолт
    `InviteCodec.DEFAULT_TTL_MS` = 48ч). 1–24 часа шагом в час, дальше отдельное
    состояние «Без ограничений» (технически 100 лет — см. `TTL_INFINITE_MS` в
    `ChatsListActivity`, чтобы не переполнить `System.currentTimeMillis() + ttlMillis`
    в `InviteCodec.encodeGroup`). Слайдер как первый вариант UI отклонён пользователем
    (риск мисдрэга на security-значимом выборе, несогласованность с существующим
    дискретным паттерном участник-лимита) — заменён на степпер по итогам обсуждения.
    Прокидывается в уже существующий параметр `InviteCodec.encodeGroup(ttlMillis=...)`,
    сам `InviteCodec.kt` не менялся — проверка `expiry` на `decode()` уже была реализована
    раньше и работала на дефолте.
