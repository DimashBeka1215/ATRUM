# Аудит Bluetooth-пути сообщений (Atrum)

Дата: 2026-06-17. Метод: статический анализ рабочего дерева через bash (gradle-сборка
в песочнице недоступна — Android SDK нет, см. CLAUDE.md §3.1, fallback = ручной ревью).

Путь BT = третий транспорт: `BleManager` (BLE-движок) → `BluetoothTransport`
(`ChatTransport`) → `SyncEngine`/`ChatActivity`. Обмен handshake/invite в
`CreateChatActivity`/`JoinChatActivity`.

## 1. Высокая серьёзность

### 1.1 GATT без шифрования и аутентификации канала
`startGattServer` объявляет характеристики с `PERMISSION_WRITE`/`PERMISSION_READ`, а не
`*_ENCRYPTED`/`*_ENCRYPTED_MITM` (BleManager.kt:225, 230). Бондинг/пейринг не требуется.
Любое устройство рядом может подключиться к GATT-серверу и писать в `RX_UUID`. Контент
зашифрован на уровне приложения (CryptoHelper), поэтому прочитать чужие сообщения нельзя,
но:
- **Засорение стора / DoS:** `onCharacteristicWriteRequest` → `handleIncoming` →
  `onMessage` → `appendLocal` пишет **любую** принятую строку на диск без проверки источника
  (BluetoothTransport.kt:62-66). Сосед может залить мусор в `bt_chat_*.dat`.
- MITM на установке канала защищён только app-слоем (identity-ключи + SAS/QR). Нужно явно
  убедиться, что BT-чат проходит ту же сверку идентичности, что и Nostr-чат.

**Рекомендация:** характеристики `*_ENCRYPTED`, требовать бондинг, либо фильтровать
входящие по подтверждённой сессии; на входе отбрасывать строки, не проходящие дешифровку.

### 1.2 Сессионный токен — всего 2 байта (16 бит)
`tokenBytes = ByteArray(2)` (BleManager.kt:142). Токен кладётся в рекламу (manufacturer
data) и в QR для матчинга. 65 536 значений → коллизии при нескольких устройствах Atrum
рядом и тривиальный перебор/спуфинг для нацеливания соединения на нужную жертву.
**Рекомендация:** ≥8–16 байт.

### 1.3 Edit/Delete по BLE ломают историю собеседника
`onMessage` всегда делает `appendLocal` — у него нет понятия «кадр редактирования/удаления».
- `replaceLine` шлёт `sendText(newLine)` (BluetoothTransport.kt:121) → у собеседника это
  придёт как **новая строка** (дубль), а не замена. Правка превращается в дубликат.
- `deleteLine` (стр. 125-130) **ничего не шлёт** собеседнику → удаление только локальное,
  у партнёра сообщение остаётся.

**Рекомендация:** ввести типы кадров (msg/edit/delete) и обрабатывать их в `handleIncoming`
с соответствующими replace/remove на стороне приёма.

### 1.4 Тихая потеря сообщений при разрыве канала
`appendLine` шлёт `runCatching { BleManager.sendText(...) }` (BluetoothTransport.kt:102) —
любая ошибка (нет соединения, BLE отвалился) **проглатывается**. Сообщение сохраняется
локально, но собеседник его не получает, а отправитель видит «доставлено». Нет ACK,
нет очереди повтора, нет seq-номеров. `BluetoothTransport` сознательно игнорирует
`onDisconnected` (комментарий, стр. 68) — UI не узнаёт о разрыве. Нарушение духа
CLAUDE.md §1.5 («всё на месте»): пользователь печатает в пустоту.
**Рекомендация:** ACK + очередь недоставленных + индикация разрыва в UI.

## 2. Средняя серьёзность

### 2.1 Меняется ГЛОБАЛЬНОЕ имя Bluetooth устройства
`runCatching { a.name = displayName }` (BleManager.kt:196) переименовывает Bluetooth-адаптер
**на уровне всей системы** (видно другим приложениям, сохраняется после выхода). Плюс имя
устройства транслируется в scanResponse всем сканерам рядом — деанонимизация.
**Рекомендация:** не трогать системное имя; передавать отображаемое имя внутри handshake
(`onHello`), а не через adapter.name.

### 2.2 Блокирующий диск-I/O в BLE-колбэке
`onCharacteristicWriteRequest` (binder-поток) → `onMessage` → `appendLocal` → `saveToDisk`
(синхронная запись файла). Блокирующая запись на потоке BLE-стека = риск джанка/ANR и
замедления GATT. **Рекомендация:** выносить запись в `Dispatchers.IO`.

### 2.3 Двойная роль (advertise+scan+server+client) без разруливания гонки
Оба телефона одновременно рекламируют, сканируют, держат GATT-сервер и могут стать central.
Если оба тапнут друг друга — поднимутся два соединения (`clientGatt` и `serverDevice` оба
заданы). Логика разрыва (BleManager.kt:248-253: `if (clientGatt == null)`) обрабатывает
двойную роль неоднозначно — возможен «полу-подключён» (одна сторона считает connected,
другая нет). **Рекомендация:** детерминированный выбор инициатора (например, по сравнению
адресов/токенов), закрывать лишнее соединение.

### 2.4 `connect()` (central) не виден целиком — нет requestMtu / discoverServices
Видимая часть `connect` обрывается. По умолчанию `mtu=20` → полезная нагрузка 20 байт,
все сообщения нарезаются на множество кадров (BLE и так медленный). Нужно убедиться, что в
утраченной части есть `requestMtu(512)`, `discoverServices()`, подписка на `TX_UUID` (запись
CCCD). Без этого приём notify не работает.

### 2.5 SyncEngine/presence крутятся вхолостую в BT-чате
Поллинг (3с) и presence-heartbeat (5с) рассчитаны на сетевой транспорт. В BT-чате
`loadAllIfChanged` читает локальный диск, presence/typing по сети не имеют смысла (нет реле).
Лишние тики/работа; presence «онлайн» недостоверен. **Рекомендация:** для BT отключить
presence/poll, опираться только на `watchMessages` + реальное состояние BLE-линка.

### 2.6 Изображения: ссылка уходит, данных нет
`uploadImage` (BluetoothTransport.kt:136-145) — заглушка, сохраняет локально и возвращает
`img_*.txt`. Но строка сообщения с этой ссылкой **уйдёт** партнёру через `appendLine`
(если медиа где-то всё же доступно) → у партнёра «битая картинка». UI вроде прячет вложения
(`btnAttach` GONE при `btMode`, ChatActivity:800), но путь `uploadImage` в транспорте открыт.
**Рекомендация:** явно запрещать медиа в BT на уровне транспорта или не слать строку-ссылку.

## 3. Низкая серьёзность / гигиена

### 3.1 `seen` растёт без очистки
`ConcurrentHashMap<String,Long>` адресов (BleManager.kt:90) не прунится (только `clear()`
в начале discovery) → медленная утечка при долгом сканировании.

### 3.2 Нет `uses-feature bluetooth_le`
Манифест объявляет `android.hardware.bluetooth`, но не `android.hardware.bluetooth_le`
(весь путь — BLE). Не критично (required=false), но стоит добавить.

### 3.3 Единственный глобальный listener — гонка при handoff
`BleManager` — `object` с одним `@Volatile var listener`. `BluetoothTransport.init` делает
`setListener(this)`, перехватывая listener у `CreateChatActivity`. На стыке
CreateChatActivity → ChatActivity события (onMessage/onDisconnected) могут потеряться, если
момент передачи не синхронизирован с `keepAlive`. Нужен ревью последовательности
`keepAlive`/`setListener`/`shutdown` (логика частично в обрезанных файлах).

### 3.4 `onMtuChanged` есть только на сервере
Переопределён в `gattServerCb` (BleManager.kt:256), но симметричный колбэк на стороне
client-GATT — в утраченной части. Проверить, что central тоже обновляет `mtu`.

### 3.5 Манифест-разрешения — в целом корректны
`BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN` (с `neverForLocation`), `BLUETOOTH_ADVERTISE`,
legacy `BLUETOOTH`/`BLUETOOTH_ADMIN` (`maxSdkVersion=30`), `ACCESS_FINE_LOCATION`
(`maxSdkVersion=30`). Замечаний нет, кроме 3.2.
