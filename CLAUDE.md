# AI Instructions — Atrum Chat

Обязательные правила для любого AI-агента работающего с этим проектом.
Нарушение любого пункта недопустимо.

---

## ⛔ ЯЗЫК ОБЩЕНИЯ — ТОЛЬКО РУССКИЙ

AI-агент ОБЯЗАН вести всё общение с пользователем **на русском языке**: объяснения,
ответы, вопросы, итоги, описания правок, сообщения об ошибках и о результате проверок.
Это жёсткое требование, без исключений.

- Комментарии в коде, коммит-сообщения и текст для пользователя — на русском.
- Технические термины и имена кода (`encrypt`, `chat.chatId`, `AES-GCM` и т.п.) можно
  оставлять как есть — но окружающий текст русский.
- Даже если пользователь написал по-английски — отвечаем по-русски.

## ⛔ ATRUM — МЕССЕНДЖЕР НА КАЖДЫЙ ДЕНЬ: ОТПРАВКА БЕСШОВНА И БЫСТРА

Фундаментальный принцип продукта. ATRUM — это мессенджер, которым пользуются каждый день.
**Любая отправка (текст, фото, голос, стикер, реакция) обязана ощущаться мгновенной,
бесшовной и быстрой.** Пользователь НИКОГДА не должен чувствовать, что что-то «грузится»,
«обрабатывается» или «сломалось». Это не пожелание — это требование к каждой правке,
затрагивающей отправку/приём.

### Обязательно при любой отправке

1. **Мгновенный оптимистичный показ.** Сообщение появляется в ленте СРАЗУ (`addOptimistic`),
   ещё до сети. Своё медиа (фото/голос) видно немедленно — берётся из локального кэша
   (`ImageCache`/битмап уже на устройстве), а НЕ серым плейсхолдером в ожидании сети.
2. **Ввод не блокируется.** Поле ввода и кнопки остаются доступными — заливка контента
   уходит в ФОНОВУЮ корутину, `unlockAfterUpload()` срабатывает сразу после показа
   оптимистичного сообщения, а не после завершения заливки по сети.
3. **Прогресс ненавязчив.** Индикатор загрузки — лёгкий слой ПОВЕРХ самого контента
   (полупрозрачный оверлей на фото), который тихо исчезает. Никаких «экранов обработки»
   вместо контента. Для мелкого контента индикатор почти незаметен.
4. **Понятный статус, мягкие ошибки.** Часики → галочка по подтверждению доставки. Сбой —
   аккуратный `failSend` (часики → ошибка) + короткий тост, а НЕ вечное «в обработке» и не
   краш. Ничего не должно «зависать» в неопределённом состоянии.
5. **Скорость — по возможности максимум, но без потери надёжности.** Сетевые оптимизации
   (число реле для заливки, параллелизм) допустимы, только если НЕ ломают доставку. Через
   Tor агрессивный burst недопустим (реле не подтверждают) — баланс в пользу надёжности;
   в прямом режиме можно быстрее. См. §1, §13.

### Запрещено

- Блокировать ввод на время сетевой заливки.
- Показывать «обработку»/серый плейсхолдер ВМЕСТО уже доступного локально контента.
- Оставлять сообщение в бесконечном «отправляется» при сбое (всегда `failSend`).
- Любые оптимизации скорости, которые приводят к «не удалось отправить».

Связано с §1.5 (всё грузится на месте) и §13 (отправка/приём медиа). Перед тем как сказать
«готово» по любой правке отправки — мысленно пройди путь глазами пользователя: появилось ли
сразу, можно ли сразу писать дальше, не выглядит ли это «сломанным».

## 0. МОКАП ПЕРЕД UI — ОБЯЗАТЕЛЕН ⛔

Перед **любым** изменением интерфейса (layout XML, drawables, цвета, отступы, типографика, анимации, новые экраны) — без исключений:

### Порядок действий

1. **Создать демо-мокап** — интерактивный HTML-виджет с визуальным представлением изменения.
   - Показать как выглядит элемент/экран до и после (если применимо).
   - Если изменение предполагает анимацию — реализовать её в мокапе (CSS/JS анимация).
   - Мокап должен отражать реальные цвета темы (тёмная по умолчанию: bg `#000000`, accent `#9D4EDD`, surface `#0A0A0A` и т.д.).

2. **Дождаться явного одобрения пользователя** — слова "ок", "делай", "хорошо", "approve" или аналог.

3. **Только после одобрения** — вносить изменения в реальные файлы проекта.

### Что считается изменением UI

- Любой layout XML файл (`res/layout/`)
- Любой drawable XML (`res/drawable/`)
- Файлы цветов или тем (`colors.xml`, `themes.xml`)
- Kotlin-код, меняющий внешний вид (setBackground, setTextColor, visibility, animations)
- Новые экраны или компоненты

### Исключения (мокап не нужен)

- Исправление crash/NPE без изменения внешнего вида
- Добавление строк локализации (`strings.xml`) без изменения layout
- Правки только в логике (транспорт, крипто, синхронизация)

### Формат мокапа

Использовать `show_widget` с HTML/CSS, имитирующим Android UI:
- Тёмный фон (`#000000`), акцент `#9D4EDD`, шрифт sans-serif
- Размер ~360×640dp (пропорции телефона)
- Подписи "До" / "После" если показываются оба варианта
- Анимация через CSS `@keyframes` или JS если нужна

### Адаптация под все режимы — ОБЯЗАТЕЛЬНА ⛔

Каждое изменение UI **обязано** корректно выглядеть в трёх режимах одновременно.
Пропустить любой из них — ошибка.

| Режим | Что проверить |
|-------|--------------|
| **Тёмная тема** | bg `#000000`, surface `#0A0A0A`, text `#FFFFFF` — элемент читаем? |
| **Светлая тема** | bg `#F2F2F7`, surface `#FFFFFF`, text `#1C1C1E` — нет белого текста на белом? |
| **Glass mode** (обои активны) | Элемент поверх произвольного фото. Только `@color/white` + полупрозрачные тёмные оверлеи. Никаких `@color/bg` / `@color/surface` как фона — они непрозрачные. |

> ⚠️ **Glass mode — режим ТОЛЬКО для экранов чата** (`ChatActivity` / `MessageAdapter` поверх обоев).
> НЕ применять glass-оформление (`bg_glass_*`, `bg_info_glass`, полупрозрачные белые фоны) на других
> экранах — профиль партнёра, настройки, join chat, списки и т.д. На нечатовых экранах всегда обычные
> непрозрачные токены `@color/surface` / `@color/bg` и обычные карточки (`bg_settings_card` и пр.).

**Алгоритм при добавлении нового UI-элемента:**
1. Тёмная тема — мысленно нарисовать на `#000000`. Всё видно?
2. Светлая тема — мысленно нарисовать на `#F2F2F7`. Нет инверсии?
3. Glass mode — мысленно поверх тёмной фотографии. Элемент читаем без непрозрачного фона?
4. Если хоть один режим сломан — сначала исправить, потом говорить что готово.

### Элементы НЕ ВРЕЗАЮТСЯ друг в друга — ОБЯЗАТЕЛЬНО ⛔

Никакие два элемента интерфейса не должны перекрывать, наезжать или вплотную упираться друг в друга. Между элементом A и элементом B всегда есть воздух — достаточно, чтобы не слипались, но не слишком много, чтобы не разваливать композицию.

Перед тем как сказать «готово», для каждого нового/изменённого UI-элемента проверить:

1. **Перекрытие** — элемент не лежит поверх другого (кроме намеренных оверлеев: оверлей загрузки, bottom sheet, диалог). Текст не заходит под иконку/кнопку, кнопки не накладываются.
2. **Минимальный зазор** — между соседними элементами есть отступ из палитры §6 DESIGN.md (Row gap 4–8dp между элементами списка, Icon–text gap 12–14dp, Section gap 20–24dp между секциями). Меньше — слипнется, и это запрещено.
3. **Не слишком далеко** — зазор не больше нужного уровня (не ставить Section gap там, где нужен Row gap). Элементы одной группы держатся вместе.
4. **Динамический контент** — при длинном тексте/имени/коде элемент переносится или обрезается (`ellipsize`/`maxLines`), но НЕ налезает на соседний. Проверить на длинном значении.
5. **Все три режима** — отступы и отсутствие наложений сохраняются в тёмной, светлой и glass.

Если хоть где-то элементы врезаются или слиплись — сначала исправить отступы/layout, потом говорить что готово.

## 1. СИНХРОНИЗАЦИЯ — НЕПРИКОСНОВЕННО ⛔

Система синхронизации работает стабильно. Любое неосторожное изменение может
сломать доставку сообщений, профилей или шифрование у всех пользователей.

### Как устроена синхронизация

```
ChatActivity.startPolling() → SyncEngine (единый single-flight polling loop)
    │
    ├── ChatTransport (интерфейс — единственная точка входа в сеть)
    │       ├── NostrTransport → NostrRelayPool → публичные реле через Tor  ← АКТУАЛЬНЫЙ
    │       │      ├── NostrMessageStore (долговечный локальный стор сообщений)
    │       │      └── RelayListStore — подписанный обновляемый список реле (additive)
    │       ├── LocalTransport → файл на диске (чат «Избранное», offline)
    │       └── BluetoothTransport → обмен по BLE (оффлайн-путь, экспериментальный)
    │
    ├── PatchQueue — сериализованная очередь всех записей (append/save/edit/delete)
    ├── MessageSendManager — анти-спам/очередь отправки текста (мимо PatchQueue)
    ├── CryptoHelper — шифрование/дешифровка всего контента
    ├── ProfileSync — синхронизация профилей через profiles.txt
    └── ImageLoader — загрузка фото через ChatTransport
```

> ⚠️ **Историческое наследие:** GitHub Gist, DeviceFlow/OAuth и DHT **полностью удалены** —
> файлов `GistApi.kt`, `GistTransport.kt`, `OAuthManager.kt`, `DeviceFlowService.kt`
> в проекте больше нет. Слово «Gist» уцелело только в **именах типов** (`AllGistData`,
> `loadAll…`) и в имени параметра `gistId`, который теперь используется лишь как соль для
> деривации ключа сообщений/реакций. Эти имена **менять нельзя** — сломается расшифровка
> существующих чатов (см. §7). Не воспринимай их как признак живого пути через GitHub.

**Главное правило:** любая новая фича общается с сетью ТОЛЬКО через `ChatTransport`.
Никогда не создавай собственный WebSocket/HTTP-клиент и не обращайся к Nostr-реле напрямую
из Activity/Fragment/ViewModel — только через `NostrTransport`/`ChatTransport`.

### Что можно

- Добавлять новые типы сообщений через существующий `Message.fromDecrypted()` / `toEncryptedLine()`
- Добавлять новые поля в `Profile` (с backward-compatible значениями по умолчанию)
- Добавлять новые файлы через `ChatTransport.saveFile()` / `loadFileOrNull()` (имена методов сохраняют семантику «файл в чате»)
- Читать и писать через `ProfileSync` для синхронизации пользовательских данных

### Что нельзя — нарушение ломает всё

- **Нельзя** создавать отдельный поллинг-цикл — весь polling идёт в одном месте (`SyncEngine`, запускается из `ChatActivity.startPolling()`)
- **Нельзя** обращаться к Nostr-реле или сети напрямую в обход `NostrTransport`/`ChatTransport`
- **Нельзя** менять формат шифрования в `CryptoHelper` без поддержки обратной совместимости — старые сообщения перестанут читаться
- **Нельзя** менять структуру `chat.txt` или `profiles.txt` без версионирования — второй телефон сломается
- **Нельзя** менять источник соли для деривации ключа (`channelId` для профилей, `gistId` для сообщений/реакций) — расшифровка существующих чатов сломается
- **Нельзя** делать сетевые запросы на главном потоке — только через `Dispatchers.IO`

### Задержки и тайминги — не трогать без явного разрешения пользователя

> Актуально для текущего транспорта — **Nostr через Tor** (значения сверены с кодом).
> Колонка «локальный» = путь без Nostr (`LocalTransport` — чат «Избранное»); это НЕ Gist
> (его больше нет), а оффлайн-fallback. Константы с суффиксом `ACTIVE_INTERVAL_MS` /
> `ACTION_TIMEOUT_MS` исторически назывались «Gist», но применяются именно к этому пути.

| Параметр | Значение | Где |
|----------|----------|-----|
| Интервал поллинга | 3 сек (Nostr) / 5 сек (локальный) | `SyncEngine.NOSTR_ACTIVE_INTERVAL_MS / ACTIVE_INTERVAL_MS` |
| Интервал в фоне | 30 сек | `SyncEngine.BACKGROUND_INTERVAL_MS` |
| Online heartbeat | каждые 5 сек | `ChatActivity.PRESENCE_INTERVAL_MS` |
| Online expiry | 20 сек без heartbeat → оффлайн | `ChatActivity.ONLINE_EXPIRY_MS` |
| Typing expiry | 14 сек без события → не печатает | `ChatActivity.TYPING_EXPIRY_MS` |
| Read receipt задержка | 500 мс после отображения | `scheduleMarkAsRead()` |
| FS-баннер порог | 6 тиков без ключа | `ChatActivity` |
| Retry read receipt | 3 попытки с паузой 2 сек | `scheduleMarkAsRead()` |
| Таймаут действия PatchQueue | 30 сек (Nostr) / 4 сек (локальный) | `PatchQueue.NOSTR_ACTION_TIMEOUT_MS / ACTION_TIMEOUT_MS` |
| Дедлайн чтения реле | 15 сек (Tor) / 8 сек (direct) | `NostrTransport.SOFT_READ_DEADLINE_TOR_MS / SOFT_READ_DEADLINE_MS` |
| Fallback с Tor на direct | 20 сек без READY → прямое подключение | `NostrTransport.TOR_FALLBACK_MS` |
| Троттл обновления списка реле | 10 мин | `NostrTransport.RELAY_REFRESH_THROTTLE_MS` |

Слишком частый поллинг/presence → публичные Nostr-реле начинают резать/отклонять
запросы (это ломает синхронизацию). Слишком редкий → видимые задержки доставки.
Таймаут действия PatchQueue ОБЯЗАН покрывать дедлайн чтения реле — иначе
edit/delete/реакции через Tor падают по таймауту.

### Forward secrecy — особая осторожность

Сессионный ключ (V3) живёт только в памяти и уничтожается при закрытии чата.
- Не сохранять `myEphemeralPrivKey` в SharedPreferences или БД
- Не логировать содержимое `sessionKey`
- После `CryptoHelper.setSessionKey()` сразу затирать локальную копию (`key.fill(0)`)
- При добавлении нового поля в Profile: если поле null — старый клиент должен продолжать работать

## 1.5 ВСЁ ГРУЗИТСЯ НА МЕСТЕ — никаких «перезайди, чтобы сработало» ⛔

Любой результат действия пользователя обязан отображаться **сразу, на текущем экране**.
Недопустима ситуация «отправил/нажал → не сработало → выйди и зайди заново, и тогда применится».

### Правило

- Любое действие (отправка сообщения/стикера/реакции, редактирование, удаление, смена
  настройки, загрузка контента) должно давать **мгновенную оптимистичную** реакцию в UI и
  **немедленно** обновлять состояние (StateFlow/адаптер) — через `emit()` / `notify*` /
  обновление `StateFlow.value`, а НЕ полагаясь только на следующий тик опроса.
- Подтверждение/откат состояния (часы → галочка, «отправлено», «ошибка») делается прямо в
  обработчике результата, а не откладывается до перезагрузки экрана.
- Если данные приходят асинхронно (сеть, декод, синк) — показываем заглушку/спиннер и
  заменяем её на месте, как только данные готовы. Перезаход не должен быть условием показа.

### Запрещено

- Удалять оптимистичный элемент из стора без последующего `emit()`/обновления, из-за чего UI
  остаётся со старым состоянием до следующего reconcile.
- Полагаться на «следующий опрос принесёт и обновит» как на ЕДИНСТВЕННЫЙ способ убрать
  индикатор отправки/загрузки.
- Любые ветки, где правильное отображение наступает только после `onCreate`/повторного входа.

### Чек-лист перед «готово»

1. Выполнил действие — результат виден **в этот же момент** на экране?
2. Часы/спиннер/«отправляется» снимаются сами, **без** выхода-входа?
3. При асинхронной загрузке заглушка заменяется на месте?
4. Если что-то меняешь в сторе — после изменения вызван `emit()`/`notify*`/обновлён `value`?

## 2. Подъём версии — ОБЯЗАТЕЛЕН после любого изменения кода

Файл: `app/build.gradle.kts`

## 3. Работа с файлами — использовать bash ⛔

Kotlin-файлы в этом проекте большие (1000–3000+ строк). Инструмент `Read` имеет лимит ~25 000 токенов и **молча обрезает** файл — конец теряется без предупреждения. Это ломает файлы при последующих правках.

**Обязательно для всех Kotlin/Gradle файлов:**

- Читать через `bash`: `cat -n file.kt`, `sed -n '100,200p' file.kt`, `grep -n pattern file.kt`
- Вносить правки через `bash`: `sed -i`, `python3` скрипт с точечной заменой
- `Read`-инструмент допустим только для коротких файлов (<200 строк) или чтения конкретного диапазона строк
- После каждой правки — немедленная проверка баланса скобок (см. раздел ниже)

**Восстановление обрезанного файла:**
```bash
git show HEAD:путь/к/File.kt | tail -50   # смотрим оригинал
wc -l путь/к/File.kt                       # сравниваем кол-во строк
```

## 3.1 Проверка синтаксиса — ОБЯЗАТЕЛЬНА перед завершением ⛔

После **каждого** изменения Kotlin/Gradle файлов — без исключений — выполнить проверку.

## 4. Цвета — только через @color, никаких hardcode

Любой новый экран/view обязан использовать цветовые токены из палитры.
Жёстко прописанные hex-значения (#FFFFFF, #000000 и т.п.) в layout-файлах и Kotlin-коде **запрещены** — иначе экран сломается в светлой или тёмной теме.

| `@color/bg` | #F2F2F7 | #000000 | Основной фон экрана |
| `@color/surface` | #FFFFFF | #0A0A0A | Карточки, блоки |
| `@color/surface_elevated` | #EAEAEF | #141414 | Приподнятые элементы |

| `@color/accent` | #9D4EDD | #9D4EDD | Акцент, кнопки, ссылки |

## 5. Светлая тема — правила проверки ⚠️

Приложение работает в двух темах (светлая / тёмная). Баги светлой темы появляются когда элемент рассчитан на тёмный фон, но отображается на белом.

### Разрешённые исключения — `@color/white` и `Color.WHITE` допустимы только в этих случаях

| Где | Почему допустимо |
|-----|-----------------|
| Текст на кнопках (`@drawable/bg_button`) | Фон всегда `accent` #9D4EDD — тёмный в обеих темах |
| Инициалы аватара (`@drawable/bg_avatar_placeholder`) | Фон всегда `accent_dark` #7B2CBF |
| Буква аватара в настройках (`@drawable/bg_avatar_purple`) | Фон — фиолетовый градиент |
| Иконка камеры на кнопке редактирования аватара | Фон `bg_edit_avatar_btn` = `@color/accent` |
| Текст своего сообщения (`item_message_self`) | Пузырёк `msg_self` #6B26B6 — тёмный в обеих темах |
| Счётчик непрочитанных (`bg_unread_badge`) | Фон `accent` — тёмный |
| ChatActivity / MessageAdapter в `glassMode = true` | Только при активных обоях, поверх фото |
| `activity_image_view` и `item_image_page` | Чёрный фон просмотрщика фото — намеренно |
| `WallpaperPreviewActivity` | Предпросмотр обоев — UI поверх фото |
| Маска ripple в `TelegramMenu.rippleOval/rippleRect` | `Color.WHITE` используется только как маска, не видна пользователю |
| `AvatarUtils.toCircle()` | Porter-Duff маска для обрезки по кругу — не видна |

### Запрещено — вызывает баги в светлой теме

- `Color.WHITE` или `#FFFFFF` на тексте/иконках без гарантированно тёмного фона
- Полупрозрачный белый (`0x22FFFFFF`, `0x44FFFFFF`) как фон UI-элементов в обычном (не glass) режиме — на белом фоне невидимо
- `stroke="#000000"` в drawables — чёрная рамка на светлых поверхностях
- Хардкод ошибочного красного (`#EF5350`, `#FF0000`) — использовать `@color/error`
- Хардкод любого purple/accent (`#A855F7`, `#9D4EDD`) в drawables — использовать `@color/accent`

### Режимы работы чата — важно для MessageAdapter

Адаптер работает в двух режимах, цвета должны выбираться явно:

```
glassMode = false (по умолчанию):
  — фон экрана: @color/bg (#F2F2F7 светлая, #000000 тёмная)
  — пузырёк партнёра: @color/msg_other (#E5E5EA светлая, тёмный серый — тёмная)
  — чипы реакций партнёра: фон @color/surface_elevated, текст @color/text_primary

glassMode = true (при наличии обоев):
  — поверх произвольного фото/фона
  — допустим Color.WHITE для текста поверх тёмного overlay
  — допустим полупрозрачный тёмный фон (0x33000000) для чипов реакций
```

### Чек-лист при добавлении нового UI-элемента

Перед завершением задачи проверить:
1. Открыть `values/colors.xml` — светлая тема. Мысленно нарисовать элемент на фоне `#F2F2F7`.
2. Если текст белый — убедиться что фон гарантированно тёмный (один из исключений выше).
3. Если используется `stroke` — цвет из палитры, не hex.
4. Если drawable содержит `solid` с цветом — токен из палитры, не hex.
5. Если элемент в `MessageAdapter` — проверить оба значения `glassMode`.

## 5.1 СВЕТЛАЯ И ТЁМНАЯ ТЕМА — ЖЁСТКОЕ ПРАВИЛО ⛔

ОБЯЗАТЕЛЬНО. Нарушение = переделка.

**На светлой теме НЕ МОЖЕТ быть белого текста и чёрных окон. На тёмной теме НЕ МОЖЕТ быть чёрного текста и белых окон. Только @color/ токены, никогда hardcode.**

### ЗАПРЕЩЕНО

```
android:textColor="#FFFFFF"
android:textColor="#000000"
Color.WHITE / Color.BLACK
#CCCCCC, #EEEEEE, #555555, #333333 — любой hardcode hex
Окна/диалоги с фоном #000000 на светлой теме
Окна/диалоги с фоном #FFFFFF на тёмной теме
```

### ОБЯЗАТЕЛЬНО

```
android:textColor="@color/text_primary"
setTextColor(ContextCompat.getColor(context, R.color.text_primary))
android:stroke="@color/border"
android:background="@color/surface"  (для окон, диалогов, карточек)
Только токены, никогда hardcode.
```

### Таблица:

| Что это | Токен | Светлая | Тёмная |
|--------|-------|---------|--------|
| Текст/Иконки | `@color/text_primary` | #1C1C1E | #FFFFFF |
| Вторичный текст | `@color/text_secondary` | #636366 | #A0A0A8 |
| Третичный текст | `@color/text_tertiary` | #6C6C70 | #6A6A75 |
| Hint/Placeholder | `@color/text_quaternary` | #8E8E93 | #3D3D45 |
| Рамки/Stroke | `@color/border` | #C6C6C8 | #1F1F1F |
| Фон окна/карточки | `@color/surface` | #FFFFFF | #0A0A0A |
| Приподнятые окна | `@color/surface_elevated` | #EAEAEF | #141414 |

### Алгоритм:

1. Новый элемент/окно → все цвета из @color/
2. textColor, backgroundColor, stroke, tint — только токены
3. Окна/диалоги → обязательно @color/surface или @color/surface_elevated
4. **После завершения: мысленно представь как это выглядит на светлой теме**
   - Видно все элементы?
   - Нет чёрных окон?
   - Текст читаемый?
5. **Мысленно представь как это выглядит на тёмной теме**
   - Видно все элементы?
   - Нет белых окон?
   - Текст читаемый?
6. **Если при визуальной проверке нашёл проблему → сразу исправь**
   - Измени цвет
   - Проверь снова
   - Только потом скажи что готово
7. Увеличить versionCode

### Исключения:

Белый текст допустим только если фон гарантированно тёмный:
- На @color/accent (#9D4EDD)
- На аватаре (#7B2CBF)
- Маска ripple (невидима)

Всё остальное → токены.

**Применяй это для ЛЮБЫХ UI-изменений. Всегда проверяй визуально перед тем как сказать что готово.**

## 6. Строки — обязательно на двух языках

Любая строка отображаемая пользователю **запрещена** в layout или Kotlin напрямую.
Всё через `@string/` ресурсы. Жёстко прописанный текст в layout/коде — ошибка.

### Структура локализации

| Файл | Содержимое |
|------|-----------|
| `values/strings.xml` | Русский (default, полный набор) |
| `values-en/strings.xml` | Английский (полный override для EN-локали) |
| `values-ru/strings.xml` | Дополнительные русские overrides (некоторые строки) |

### Правило добавления новых строк

При добавлении любой новой строки — добавить **одновременно в два файла**:

1. `values/strings.xml` — русский текст
2. `values-en/strings.xml` — английский текст

Пропустить один из файлов нельзя. Если не добавить английский — на EN-локали будет показан русский текст из default, что недопустимо.

Пример:
```xml
<!-- values/strings.xml -->
<string name="my_new_screen_title">Новый экран</string>
<string name="my_new_screen_btn">Подтвердить</string>

<!-- values-en/strings.xml -->
<string name="my_new_screen_title">New screen</string>
<string name="my_new_screen_btn">Confirm</string>
```

## 9. Иконки — только контурные drawable, emoji запрещены ⛔

**Emoji в UI запрещены.** Любой символ emoji (👍, 📷, ✓, ❤️ и т.д.) в layout, drawable или Kotlin-коде, отображаемый как элемент интерфейса, должен быть заменён контурной иконкой из `res/drawable/`.

### Правило

- Иконки — только через `<ImageView>` или `<ImageButton>` с `android:src="@drawable/ic_*"`
- Стиль: **outline** (контурные), не filled
- Цвет иконки — через `app:tint="@color/..."`, только токены из палитры
- Размер: 18–24dp для кнопок, 14–18dp для inline-элементов

### Запрещено

```xml
<!-- ❌ emoji в тексте интерфейса -->
<TextView android:text="👍" />
<TextView android:text="📷 Фото" />

<!-- ❌ emoji в коде -->
binding.tvStatus.text = "✓ Готово"
```

### Обязательно

```xml
<!-- ✓ контурная иконка -->
<ImageView
    android:src="@drawable/ic_check"
    app:tint="@color/text_secondary"
    android:layout_width="16dp"
    android:layout_height="16dp"/>
```

### Исключения

Emoji допустимы **только** в пользовательском контенте (текст сообщений, имена чатов) — то, что пишет пользователь, не трогать.

1. Получить доступ к папке проекта (уже есть через Cowork).
2. Проверить репо через bash:

3. Если remote не настроен — сообщить пользователю и попросить настроить.
4. Только после этого — приступать к задаче.

## 11. Смотреть на задачу с разных сторон — проверять связанные места ⛔

При решении ЛЮБОЙ задачи не ограничивайся одним местом. Быстро пробегись по
пунктам/экранам/компонентам, которые логически связаны с изменением, и проверь,
не нужно ли поправить и их.

> Пример: поменяли обои по умолчанию в чате (`ChatActivity.applyWallpaper`) — сразу

> противоречивом состоянии.

### Алгоритм перед «готово»

1. **Что я изменил?** — поведение, данные или внешний вид.
2. **Кто ещё это читает / показывает / дублирует?** — другие экраны, превью, миниатюры,

3. **Согласованы ли эти места с изменением?** Если нет — поправить в той же сессии.
4. Только потом говорить, что готово.

Это не про раздувание скоупа, а про согласованность: одно изменение не должно
оставлять связанные места в противоречивом состоянии.

## 13. ОТПРАВКА И ПРИЁМ МЕДИА (фото / голос / стикеры / превью) ⛔

> ⛔ Медиа-контент ОБЯЗАН шифроваться ТЕМ ЖЕ ключом, что и текст сообщений —
> сессионным (forward secrecy), а НЕ паролём. Нарушение = у собеседника медиа
> приходит «пустым» (не расшифровывается). Это стоило 7 часов отладки — не повторять.

### Как это работает (актуальная схема)

```
sendImage()/sendVoice()/стикер/превью
  │
  ├─ 1. Оптимистичное сообщение в UI сразу (chatStore.addOptimistic), часики.
  ├─ 2. Строка-сообщение (с DC1-ссылкой на файл) шифруется encrypt(.., chat.chatId).
  ├─ 3. КОНТЕНТ медиа шифруется encrypt(base64, chat.chatPassword, chat.chatId)
  │     → попадает в forward-secrecy сессию (V4-S), как текст. В ФОНЕ.
  ├─ 4. transport.appendLine(encryptedLine, extraFiles = { имя → шифртекст })
  │       └─ ПОРЯДОК: сначала контент (saveFile/чанки+манифест), ПОТОМ строка-анонс.
  │       └─ saveFile: если контент > NOSTR_CHUNK_CHARS (48 000) → чанкуется;
  │          манифест "CHUNKED:N" шифруется encrypt(.., sourceId) = тот же домен.
  │
Приём: ChatActivity → MessageAdapter.bindImage()/bindVoice()
  │
  ├─ Message.fromDecrypted() парсит DC1-ссылку → imageFileName / voiceFileName.
  ├─ ImageLoader(api, password, cryptoChatId = api.cryptoChatId).
  │     loadFromChatContent() → loadFile(имя) → decrypt(.., cryptoChatId)
  │     если CHUNKED → assembleChunkedImage() → склейка чанков → decrypt(.., cryptoChatId).
  └─ cryptoChatId = chat.chatId (домен сессии), НЕ channelId.
```

### Как ДОЛЖНА работать (жёсткие правила)

1. **Крипто-домен медиа = `chat.chatId`, не `channelId`.** Контент, манифест и приём
   используют `chat.chatId` (он же `transport.cryptoChatId` / `sourceId`). Под этим же
   доменом ставится forward-secrecy сессия (`setSessionKey(chat.chatId, …)`), поэтому
   `encrypt()` автоматически берёт сессионный ключ (V4-S), а не парольный.
   - ⛔ НЕ шифровать медиа через `encryptFileContent`/`encryptV4` и НЕ по `channelId`:
     это парольный ключ (Argon2). При разных паролях или forward-secrecy он не совпадёт,
     и у собеседника медиа будет «найден, но не расшифровался».
2. **Сеть и крипто — РАЗНЫЕ chatId.** `channelId` (= hash от `chat.chatId`) — ТОЛЬКО для
   тегов Nostr (`#t`, wireName файлов). `chat.chatId` (`cryptoChatId`) — ТОЛЬКО для
   шифрования/расшифровки контента. Не путать.
3. **Порядок в `appendLine`:** сначала залить контент (чанки+манифест), потом публиковать
   строку-анонс. Иначе получатель увидит сообщение раньше, чем медиа доступно на реле.
4. **Чанкование:** контент > `NOSTR_CHUNK_CHARS` (48 000) режется; каждый чанк — отдельное
   FILE_KIND-событие, манифест шифруется тем же доменом (`sourceId`). Размер чанка не
   повышать — крупные события реле режут/отклоняют.
5. **Всё на месте (см. §1.5):** оптимистичное сообщение и снятие часиков — сразу; заливка
   контента в фоне, не блокирует ввод; при сбое — `failSend` (часики → ошибка), не «вечная
   обработка».
6. **Совместимость чтения:** `CryptoHelper.decrypt()` автодетектит формат по префиксу
   (V4-S/V3/V4/V5/V2/V1) — на чтении менять ничего не нужно. Старое медиа, зашифрованное
   парольным V4, НЕ перешифровывается задним числом и может остаться нечитаемым — это
   нормально, лечится переотправкой.

### Диагностика (если медиа «пустое»)

- По тапу на нерасшифрованное фото / по play голосового — тост с причиной
  (`ImageLoader.diagnoseMedia`): «не найден на реле» / «не расшифровался (fmt=…)» /
  «манифест: N чанков» и т.д. Причина копируется в буфер.
- `fmt=$G4S$` — сессионный (норма для нового медиа); `fmt=$G4$` — парольный V4 (старое или
  ошибочный путь); сверка ключа — `CryptoHelper.v4KeyHash(password, chatId)`.

### Критические файлы медиа

| Файл | Назначение |
|------|-----------|
| `ChatActivity.sendImage/sendImages/sendVoice` | Шифрование контента `encrypt(.., chat.chatId)` + `appendLine` |
| `transport/NostrTransport.saveFile/saveFileChunked` | Публикация контента/чанков, манифест `encrypt(.., sourceId)` |
| `transport/ChatTransport.cryptoChatId` | Крипто-домен (= sourceId у Nostr), отдельно от `chatId` (сеть) |
| `ImageLoader` | Приём: загрузка + `decrypt(.., cryptoChatId)`, склейка чанков |
| `ImageChunker` | Манифест/чанки (`CHUNKED:N`, `chunkName`) |
| `Message.composePlaintext/fromDecrypted` | DC1-ссылка на медиа в строке-сообщении |

## 14. ВНУТРЕННИЙ АУДИТ И ТЕСТИРОВАНИЕ ДОБАВЛЕННЫХ ФУНКЦИЙ ⛔

После добавления или существенной правки функции — и время от времени по ходу крупной
задачи — AI-агент ОБЯЗАН провести **внутренний аудит и тестирование** того, что сделал,
прежде чем сказать «готово». Это не разовая формальность в конце, а периодическая привычка:
если фича растянулась на много правок, прогоняй аудит промежуточно, а не только в самом конце.

### Когда проводить

- После завершения новой функции (экран, компонент, поток отправки/приёма и т.п.).
- Периодически внутри длинной задачи — не копить весь аудит на финал.
- Всегда, когда пользователь просит «проверь / протестируй / проведи аудит».

### Что проверять (чек-лист)

1. **Мигание и перерисовка.** Нет ли лишних полных ребайндов (`notifyDataSetChanged` там,
   где хватит точечного `notifyItemChanged`)? Не декодируется ли контент заново при каждой
   перерисовке (нужен кэш битмапов/миниатюр)? Change-анимации RecyclerView отключены там,
   где они дают fade-мерцание. См. §1.5 (всё на месте) и принцип бесшовной отправки.
2. **Кликабельность.** Каждый интерактивный элемент имеет обработчик и реально кликается;
   соседние/дочерние вью не перехватывают тап; оверлеи (крестик, бейдж) не блокируют нужный
   клик и наоборот.
3. **Гонки и lifecycle.** Общее состояние меняется только с главного потока; тяжёлая работа —
   на `Dispatchers.IO`, результат применяется на main с проверкой актуальности; корутины
   привязаны к `lifecycleScope`; нет утечек диалогов/битмапов.
4. **Три темы (§0, §5, §5.1).** Элемент читаем в тёмной, светлой и (для чат-экранов) glass;
   только токены `@color/*`, без hardcode; нет белого-на-белом и чёрного-на-чёрном.
5. **Отступы и наложения (§0).** Элементы не врезаются друг в друга, зазоры из палитры,
   длинный контент переносится/обрезается, а не налезает.
6. **Согласованность (§11).** Связанные экраны/превью/дефолты обновлены под изменение.
7. **Синтаксис и целостность (§3, §3.1).** Баланс скобок, файл не обрезан, сборка (или ручной
   ревью, если `gradlew` недоступен). Сообщить пользователю результат проверки честно.

### Как оформлять

- Кратко перечислить пользователю: что проверено, что нашёл, что починил. Без воды.
- Найденные баги чинить в этой же сессии (или явно проговорить, если нельзя), затем
  поднять версию (§2) и перепроверить.
- Мысленно пройти путь глазами пользователя: сразу ли появилось, можно ли сразу
  продолжать, не выглядит ли «сломанным».
